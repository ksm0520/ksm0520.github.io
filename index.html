TRUVEL / RENDERING04 / 12

데이터의 성격에 맞춰 렌더링 경계를 나누다.

SSG · ISR · Dynamic SSR

공개 소개는 SSG, 공통 여행지 목록은 1시간 ISR, 요청마다 달라지는 검색은 Dynamic SSR로 분리했습니다. 지도·일정 등 상호작용이 많은 화면은 CSR을 유지했습니다.

193.7 → 81.6 ms초기 도시 목록 표시 중앙값 · 57.9% 단축
  1. 01

    초기 데이터 준비

    국가·도시를 서버에서 병렬 조회하고 초기 props로 전달해 브라우저 데이터 API 2회 → 0회.

  2. 02

    검색 상태 복원

    keyword·countryId를 URL에 저장하고 서버 조회로 공유·새로고침·뒤로가기를 지원.

  3. 03

    비용도 함께 확인

    SSR 검색 표시 중앙값은 138 → 216ms. 속도보다 상태 복원과 요청 구조 개선에 의미를 두었습니다.

로컬 production + 실제 Docker 백엔드 / 406×661 / 브라우저 캐시 OFF / throttling 없음 / 5회 중앙값. 운영 환경의 보편적 성능 수치가 아닙니다.

TRUVEL / RELIABILITY05 / 12

테스트의 통과보다, 반복 가능한 신뢰성.

Playwright E2E × GitHub Actions

개별 기능 테스트만으로 놓치기 쉬운 로그인·여행 생성 흐름을 E2E로 검증했습니다. CI의 서버 준비 타이밍과 공유 상태 충돌을 실행 환경의 문제로 나눠 해결했습니다.

80 / 804개 시나리오 × repeat-each=20 통과
  1. 01

    서버 준비를 명시

    프론트엔드와 백엔드 readiness를 확인한 뒤 브라우저 테스트를 시작하도록 구성.

  2. 02

    병렬성의 비용을 조정

    CI 실행을 workers=1로 제한해 테스트 간 공유 상태 충돌을 줄이고 반복 실행으로 확인.

  3. 03

    관련 변경에만 E2E

    paths-filter로 실행 조건을 나눠 E2E 미관련 PR의 워크플로 시간을 4m33s → 1m19s로 단축.

80/80은 당시 고정 시나리오의 반복 검증 결과입니다. 약 71% 시간 단축은 E2E를 생략하는 미관련 PR 조건에 한합니다.

TRUVEL / SERVER STATE06 / 12

캐시를 더하기 전에, 갱신 규칙부터 맞추다.

Predictable server state

화면마다 흩어진 실패 처리·queryKey·갱신 범위를 공통 정책으로 정리했습니다. 어떤 데이터가 언제 다시 조회되는지 코드에서 읽히도록 만드는 데 집중했습니다.

정의
queryOptions로 key·queryFn·staleTime 통합
검색
placeholderData: keepPreviousData
변경
여행별 무효화 · 삭제 낙관적 업데이트
  1. 01

    검색 중 목록 유지

    요청 사이에 이전 데이터를 유지해 목록이 사라졌다 다시 나타나는 흐름을 완화.

  2. 02

    삭제 실패까지 고려

    대상 여행 쿼리를 취소하고 캐시에서 즉시 제거한 뒤, 실패하면 이전 목록으로 rollback.

  3. 03

    재조회 범위를 제한

    저장·삭제 후 해당 여행의 장소 쿼리를 무효화하고 최종 서버 상태와 동기화.

상세 진입 클릭 시 prefetch 요청은 존재하지만, 현재 상세 페이지는 직접 API를 조회합니다. 캐시 재사용 효과는 성과로 포함하지 않았습니다.

NEUROCARE / PERFORMANCE08 / 12

로딩 점수 너머, 실제 렌더 루프를 보다.

Three.js particle rendering

Lighthouse만으로 설명되지 않는 파티클 애니메이션의 실행 비용을 DevTools Performance로 확인했습니다. 리소스를 늦게 읽는 일과 매 프레임의 연산을 줄이는 일을 나눠 접근했습니다.

488 → 148 ms약 3초 Performance 기록 내 스크립트 실행 합계
  1. 01

    장치에 맞춘 부하

    화면 폭에 따라 8,000/5,000개 파티클을 선택하고 Three.js를 동적으로 로딩.

  2. 02

    시간을 기준으로 갱신

    30fps 목표의 프레임 스킵과 deltaTime을 적용해 렌더 빈도와 애니메이션 속도를 분리.

  3. 03

    반복 할당을 줄임

    파티클 반복문 밖의 Vector3를 재사용. 매 animate 호출의 객체 생성은 여전히 남아 있습니다.

약 70%는 기록 구간의 스크립트 실행 감소율입니다. 전체 로딩 시간·TBT·FPS 개선율과 구분합니다. 30fps 제한과 GPU 설정에는 품질·전력의 절충이 있습니다.

NEUROCARE / END TO END10 / 12

화면의 입력을, 저장 가능한 결과까지.

Drawing analysis pipeline

프론트엔드에 필요한 결과가 어떻게 만들어지고 저장되는지까지 연결했습니다. FastAPI에서 업로드·분석·저장 흐름을 구현해 그림 검사와 리포트 사이의 데이터 경계를 다뤘습니다.

입력
그림 파일 + report_id
처리
S3 업로드 → GPT Vision 분석
저장
drawing_test 생성 → Report 갱신 → 응답
  1. 01

    리포트 연결 확인

    요청의 report_id로 연결할 리포트 존재 여부를 확인한 후 업로드를 진행.

  2. 02

    이미지와 분석 연결

    S3 이미지 URL을 분석 요청에 사용하고 점수·분석 결과를 정리.

  3. 03

    조회 가능한 결과로

    이미지 URL과 점수를 저장하고 리포트의 그림 점수·분석 내용·위험도 필드를 갱신.

이력서의 담당 내용과 drawing/service.py를 대조했습니다. 전체 AI 모델이나 의료적 판정 체계를 독자 설계한 것으로 표현하지 않습니다.
